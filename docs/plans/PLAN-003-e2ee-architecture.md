## Overview

This implementation plan details the phases required to migrate the current Server-Side Encryption (SSE) credential vault to a Zero-Knowledge End-to-End Encryption (E2EE) architecture. The migration involves extensive changes to the database schema, removing global encryption logic from the backend, introducing Google OAuth 2.0 for identity management, and implementing robust Web Crypto API logic in the frontend for key derivation and data encryption.

## Implementation Phases

### Phase 1: Database & Backend Preparation

- [ ] Task 1.1: Create a new Alembic migration to update the `users` table. Add columns: `public_key` (TEXT), `encrypted_private_key` (TEXT), and `key_salt` (VARCHAR).
- [ ] Task 1.2: Update the `credentials` table to support arbitrary encrypted JSON payloads (if not already supported). Replace individual encrypted fields (`encrypted_password`, `encrypted_username`, etc.) with a single `encrypted_data` JSONB or TEXT column. 
- [ ] Task 1.3: Update SQLAlchemy models (`app/models/user.py`, `app/models/credential.py`) to reflect the schema changes.

**Deliverables**: Database schema capable of storing E2EE cryptographic material.

### Phase 2: Refactoring Backend API & Identity

- [ ] Task 2.1: Remove `ENCRYPTION_KEY` dependency from `app/core/security.py` and remove server-side AES encryption/decryption utility functions.
- [ ] Task 2.2: Implement Google OAuth 2.0 flow using `authlib` or `httpx` in a new `app/api/v1/endpoints/oauth.py` router.
- [ ] Task 2.3: Modify the existing JWT authentication flow. The backend should issue a JWT purely based on successful Google OAuth verification. 
- [ ] Task 2.4: Update User creation API to accept the `public_key`, `encrypted_private_key`, and `key_salt` generated by the frontend.
- [ ] Task 2.5: Update Credential CRUD API to purely store and retrieve the `encrypted_data` blob, acting as blind storage.

**Deliverables**: A stateless, blind-storage API backend running Google OAuth authentication.

### Phase 3: Frontend Cryptography & Integration

- [ ] Task 3.1: Integrate Google OAuth login button in the Vite/React frontend.
- [ ] Task 3.2: Implement a secure `crypto.ts` utility using the Web Crypto API. Include functions for generating RSA-OAEP key pairs, AES-GCM encryption/decryption, and Argon2id key derivation (via WASM library).
- [ ] Task 3.3: Implement the "Vault Setup" flow: After a new Google OAuth registration, prompt for a Vault Password, generate the keys, and upload to the backend.
- [ ] Task 3.4: Implement the "Vault Unlock" flow: After Google Login, prompt for the Vault Password, derive the Master Key, fetch and decrypt the Private Key from the backend, and store it securely in a Web Worker or memory context.
- [ ] Task 3.5: Update the Dashboard/Credential list UI to decrypt vault items on-the-fly using the unlocked Private Key.

**Deliverables**: Fully functional E2EE frontend UI.

## Technical Decisions

- Decision 1: **Argon2id for Key Derivation** because it is memory-hard and provides superior resistance to GPU brute-forcing compared to PBKDF2, crucial for E2EE master keys.
- Decision 2: **RSA-OAEP vs ECDH** because Web Crypto API support for RSA-OAEP is universally standard for asymmetric encryption operations in browsers.
- Decision 3: **Blind Storage Backend** because it mathematically guarantees zero-knowledge security, satisfying the user's primary security requirement.

## Testing Strategy

- **Unit Tests**: Test the new OAuth login functions in `tests/api/test_oauth.py`. Test backend CRUD operations to ensure they accept and return blind ciphertext correctly.
- **Integration Tests**: Simulate the frontend's cryptographic flow to verify that payload encryption and decryption matches expectations when passed through the API.
- **Manual Testing**: User completes the full flow: Login with Google -> Set Vault Password -> Add Credential -> Logout -> Login again with Google -> Unlock Vault -> Verify Credential decrypts.

## Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|------------|
| Argon2id WASM Performance | Medium | We will benchmark the iterations/memory cost parameters to ensure the derivation completes within 1 second on average mobile devices. |
| User forgets Vault Password | High | Implement a warning during setup. We cannot mitigate data loss if the password is forgotten in a true E2EE system. Provide export functionality so users can backup. |
| Incomplete Migration of existing data | High | Advise users to export existing plain/SSE credentials before applying Phase 1, or wipe the DB for fresh installations. |
